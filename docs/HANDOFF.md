## Цель проекта

Последовательно искать воспроизводимый edge для crypto perpetual futures, не выдавая удачный исторический участок за готовую стратегию. Исследование должно учитывать реальное исполнение BingX, комиссии, funding, slippage, multiple testing и закрытый holdout.

## Текущий лучший кандидат

Исследовательский кандидат, а не готовая торговая система:

- инструмент: `ETHUSDT` perpetual;
- направление: long;
- таймфрейм: 1h;
- сигнал: сильное положительное отклонение от 24-часового VWAP (`vwap_distance_24`, верхний квартиль);
- фильтры: медвежий режим BTC и высокая волатильность;
- stop: 1.5 ATR;
- take profit: 2.0 ATR;
- максимальное удержание: 24 часа.

Validation при полных смоделированных расходах 0.10%:

- 43 сделки;
- expectancy: `+0.286R`;
- total: `+12.30R`;
- Profit Factor: `2.04`;
- win rate: `58.14%`;
- max drawdown: `-3.15R`;
- доходность: `+36.96%`.

Главное ограничение: train почти нейтрален (`PF 1.048`), доверительный интервал включает ноль, а кандидат выбран после перебора 2 016 конфигураций. Закрытый test не открывался и должен оставаться нетронутым.

## Комиссия BingX: не потерять контекст

Пользователь сообщил ставку taker `0.05%` и небольшой размер депозита.

Если `0.05%` списывается **за каждое исполнение**, полный вход и выход дают примерно `0.10%` round-trip: `0.05%` при открытии плюс `0.05%` при закрытии. Если выписка аккаунта показывает `0.05%` уже за полный круг, основной baseline должен использовать именно `0.05%`.

Не спорить об этом абстрактно: ближайшая практическая задача — проверить один полный вход/выход по фактической выписке BingX. Для небольших ордеров BTC/ETH market impact ожидается минимальным, поэтому slippage нельзя искусственно завышать; его следует измерить на paper/live fills.

Рабочие cost-сценарии до подтверждения выпиской:

| Сценарий | Round-trip cost | Роль |
|---|---:|---|
| Пользовательский минимум | 0.05% | если подтверждён полный круг |
| Taker/taker | 0.10% | если 0.05% взимается с каждой стороны |
| Реалистичный | 0.11–0.12% | комиссия и малый slippage |
| Стресс | 0.16% | только sensitivity, не основной gate |

Funding считать отдельно по timestamps удержания.

## Согласованная первая фаза

Пользователь решил двигаться небольшими фазами и потребовал обязательный handoff при каждой фазе. Сейчас первым отдельным действием публикуется именно этот handoff. Реализация Phase 1 после этого ещё не начата.

Phase 1 — технический аудит замороженного ETH-кандидата:

1. Перенести в репозиторий минимально необходимые `research/*` и тесты из исходного архива.
2. Зафиксировать machine-readable specification кандидата и границы train/validation/test.
3. Не открывать test, не запускать walk-forward и не менять параметры ради улучшения результата.
4. Проверить отсутствие look-ahead, вход после закрытого сигнала, stop/take и неоднозначную свечу, gaps, перекрывающиеся позиции, комиссии по сторонам, funding и качество данных.
5. Добавить полный trade log: timestamps, prices, stop/take, gross return, fee per side, funding, slippage, net return, initial risk, R, duration и exit reason.
6. Воспроизвести baseline только на train/validation и сверить его со snapshot.
7. Сохранить audit report, тесты и компактные артефакты.
8. Обновить этот handoff, закоммитить и запушить фазу.

Подробный утверждённый план Phase 1 существовал в предыдущем чате как `v0_plans/pure-path.md`, но plan-файл не является частью репозитория. Перечень выше — его достаточное резюме для продолжения.

## Definition of done для Phase 1

- Исследование запускается из чистого clone без зависимости от временного архива.
- Все unit/regression tests проходят.
- Test range не читался.
- Baseline train/validation либо совпадает со snapshot, либо расхождение явно объяснено.
- В Git нет market-data cache, секретов, bytecode и временных файлов.
- `docs/HANDOFF.md` обновлён фактическим результатом фазы и одним следующим шагом.

## Следующий конкретный шаг

После публикации этого handoff: получить исходный архив с модулями `research/*`, перенести только минимальный движок и тесты, затем начать аудит baseline. Если архив недоступен в новом чате, попросить пользователя приложить его снова; не восстанавливать критическую backtest-логику по памяти.

## Правила работы для следующих чатов

- Работать только в `hypothesis-analysis-results`, не пушить в `main`.
- Делать одну небольшую фазу за раз.
- Перед изменениями читать этот handoff и актуальные отчёты.
- Не переоптимизировать замороженный кандидат.
- Не открывать закрытый test до завершения audit, walk-forward и parameter stability.
- Не считать отдельное убыточное окно автоматическим провалом.
- Не использовать 0.16% как единственную модель расходов.
- В конце каждой фазы обязательно обновлять этот файл: последний коммит, сделанное, результаты, ограничения и ровно один следующий шаг.
